## 2026-11-10：真实 Shell 串口吞吐验收

- 实测 Windows / CH340（COM6）连接 riscv64 开发板的真实 Shell；原配置为 115200、8N1。设备报告 ttyS0 的 uartclk 为 24000000。测试使用 debug Serial Worker 的 stream 模式，设备上的 Shell 仅用于启动测速程序，经真实 JSON 控制协议、输出事件和每块 16 KiB 的 serial.write；不包含 xterm 渲染、MCP 或审批耗时。
- 115200 每方向 3 × 64 KiB；500000 和 1500000 最终各每方向 10 × 128 KiB。最终负载由块序号的 SHA-256 文本拼成，接收逐字节校验、设备接收整段 SHA-256 校验全部通过，两档最终测试事件缺口均为 0。平均吞吐如下，KB/s 为十进制：

| 波特率 | 接收 KB/s | 发送 KB/s | 发送范围 KB/s |
|---|---:|---:|---:|
| 115200 | 11.54 | 9.55 | 9.36–9.72 |
| 500000 | 49.98 | 36.88 | 35.06–39.35 |
| 1500000 | 135.39 | 87.59 | 76.90–94.30 |

- 230400 / 460800 / 921600 / 1000000 / 2000000 / 2500000 / 3000000 的调速握手出现乱码或超时；3500000 / 4000000 被本机驱动拒绝打开。直接使用系统 SerialPort 接口在 230400 下也不能匹配设备标记。因此 1500000 是本次硬件组合已验证的最高档位，不能据此断言 Coterm 软件的通用吞吐极限，也不能假定所有更低标准档位均可用。
- 原始结果保存在本地忽略目录 target/serial-throughput-65536.json、target/serial-throughput-sustained.json、target/serial-throughput-verified.json。后者是最终顺序变化负载的 40 个样本；接收阶段从 BEGIN 后计时，发送阶段包含分块调用、设备接收和确认，不把握手或调速时间算入有效吞吐。
- 设备端测速程序只驻留内存，正常退出及 30 秒无命令时恢复原 tty 属性；主机确认恢复后关闭端口。最终再次读取设备 termios，确认 B115200、ECHO、ICANON 均已恢复，Shell 提示符可用，COM6 已释放；没有修改已保存实例配置。
- 可复测入口：[测速脚本](../../../../scripts/benchmark-serial.mjs)、[操作步骤](usage.md#真实-shell-串口吞吐)。脚本语法检查和真实设备验收通过，无新增依赖或运行时接口变更。
