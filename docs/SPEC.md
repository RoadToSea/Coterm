# Coterm 全局技术路线与架构规格

> **CLI**: `coterm`
> **产品定位**：面向软硬一体与边缘计算场景的人机协同通信工具。
> **文档职责**：定义 Coterm 的长期架构边界和技术原则。插件运行时、MCP 接入和阶段交付细节放在 [docs/architecture](architecture/) 与 [docs/technical-plan](technical-plan/) 中。

## 1. 项目目标

Coterm 源于 SSH、串口等通信工具与 Agent 之间缺少共享交互界面的问题：Agent 能调用通信能力，但用户无法在同一会话中输入密码、观察过程或接管操作；传统桌面通信工具能显示和操作连接，却不能向 Agent 提供 MCP 能力。

Coterm 因此不试图重新实现所有通信协议，也不把不同协议强行抽象成同一种终端。它提供一个最小的桌面运行容器，让开源插件同时拥有：

- 协议连接和协议数据管理；
- 协议领域的用户界面；
- 协议原生的 MCP 能力；
- 与用户和 Coterm 基座协同所需的运行时接口。

## 2. 总体原则

1. **基座最小化**：基座提供插件生命周期、界面挂载、公共交互和运行时通信，不实现具体通信协议。
2. **插件完整化**：插件负责协议连接、协议状态、数据模型、领域界面和原生 MCP 工具。
3. **协议语义归插件**：SSH 的命令边界、UART 的原始字节、MQTT 的订阅语义、Modbus 的寄存器模型都由对应插件定义。
4. **公共能力与领域能力分离**：基座提供通用运行时 API 和可选 UI 组件，不要求插件使用统一的业务模型。
5. **用户与 Agent 共享会话**：插件的 MCP 调用和插件界面必须能关联到同一连接实例，使用户可以观察、输入、确认或中止。
6. **凭据不暴露给 Agent**：秘密通过基座提供的受控交互进入插件，不出现在 MCP 返回值、普通事件和日志中。
7. **可替换和可扩展**：插件可以独立开发、测试、发布和升级，基座不依赖某一种协议的内部实现。

## 3. 总体架构

```text
┌──────────────────────┐       MCP        ┌────────────────────────┐
│      外部 Agent      │ <--------------> │  Coterm MCP Bridge     │
└──────────────────────┘                  │  单一入口、薄路由层      │
                                          └───────────┬────────────┘
                                                      │ 原样转发
┌─────────────────────────────────────────────────────▼──────────┐
│                    插件原生 MCP Server                         │
│             SSH / UART / MQTT / 自定义协议                      │
└──────────────────────────────┬────────────────────────────────┘
                               │ 插件后端运行时接口
┌─────────────────────────────▼─────────────────────────────────┐
│                         Coterm 基座                             │
│ 插件生命周期 | 界面挂载 | 用户输入 | 凭据交互 | 公共 IPC | 路由   │
└───────────────┬──────────────────────────────┬─────────────────┘
                │                              │
       ┌────────▼────────┐             ┌───────▼────────────────┐
       │   插件后端进程    │             │     插件前端模块         │
       │ 协议连接与数据    │             │ 自定义界面或通用组件      │
       └────────┬────────┘             └────────────────────────┘
                │
       ┌────────▼────────┐
       │ SSH / UART / MQTT│
       │ 及其他通信协议    │
       └─────────────────┘
```

基座对外提供一个 MCP Bridge，作为 Agent 的单一入口；Bridge 只负责插件发现、命名空间、路由和生命周期关联，不重新定义或包装插件的领域工具。插件仍然是 MCP Server 的实现者。

当前 MVP 的实际组件关系与操作审批流程见[当前已实现架构图](architecture/current-architecture.md)；已完成能力和未实现边界见[架构与实现状态](architecture/interface-review.md)。2026-10-26 的阶段判断、优先缺口和验证结果见[项目进度评估](PROGRESS.md)。

## 4. 模块职责

| 模块 | 负责内容 | 不负责内容 |
|---|---|---|
| Tauri + Rust 基座 | 插件安装/启动/停止、插件实例、界面容器、公共 IPC、用户输入和凭据交互、MCP 注册/转发 | SSH、UART、MQTT 等协议语义和领域数据模型 |
| 插件后端 | 连接、协议状态、协议数据、领域操作、原生 MCP、数据缓存和重连 | 基座窗口布局和其他插件状态 |
| 插件前端 | 领域界面、数据呈现、用户操作、可选通用组件 | 直接访问宿主内部状态和其他插件实例 |
| 通用 UI 组件 | 终端、命令块选择、日志、表格、原始流等可复用呈现能力 | 规定所有插件必须使用相同界面 |
| MCP Bridge | 发现、路由、命名空间、调用关联 | 统一所有插件的工具参数和返回值 |

插件模块的详细运行方式见 [插件运行时与前端模块](architecture/plugin-runtime.md)，MCP 关系见 [插件原生 MCP 集成](architecture/mcp-integration.md)。

## 5. 插件模型

一个插件是“后端进程 + manifest + 原生 MCP”的完整能力单元，前端模块是可选的。插件可以只提供无 UI 的 MCP/后台服务，也可以额外提供自己的 Web 前端。后端可以使用 Rust、Go、Python、Node.js 等语言；前端使用 Web 技术实现，以便挂载到 Tauri WebView。

插件通过 manifest 声明：身份和版本、后端启动入口、前端入口、MCP 入口、所需公共能力、可创建的连接类型和资源限制。manifest 是发现和装配信息，不是把协议语义交给基座解析。

插件前端可以使用基座提供的通用组件，也可以完全自定义界面。SSH 可以使用终端和命令块组件，MQTT 可以使用 Topic 和消息表格，自定义协议可以使用自己的图形化控制面板。

第一阶段采用同一 Tauri WebView 中的受控模块加载，优先快速验证插件能力；它提供 API 和生命周期边界，不等于安全沙箱。面向第三方市场的隔离、签名和权限模型作为后续改进另行设计。

## 6. 统一运行时边界

基座与插件只统一以下运行时能力：

- 插件启动、停止、健康状态和实例生命周期；
- 插件前端挂载、卸载和实例标识；
- 前端与插件后端之间的请求、事件和数据通道；
- 用户文本、确认、密码和取消等公共交互请求；
- 可选的通用 UI 组件和主题能力；
- 插件 MCP Server 的注册、路由和会话关联。

插件前端必须通过基座提供的运行时 API 与插件后端通信；不能绕过基座直接访问本地进程或其他插件。连接、操作、订阅、消息、命令块、报文和事务等领域对象由插件定义和保存。基座只负责运行时传输、界面分发和实例关联，不把它们合并成一个全局业务模型。

## 7. 安全与可靠性底线

- 插件进程隔离用于降低崩溃影响，不自动等同于操作系统沙箱；
- 高风险用户操作应由插件发起请求、由基座提供确认交互并形成审计事件；
- 凭据通过基座的秘密输入交互传递给插件，禁止进入 Agent 上下文、普通插件事件和日志；
- 高频数据由插件负责协议级缓存和解析，基座运行时必须提供有界队列、背压、取消和断线状态；
- 插件崩溃、连接断开和宿主重启后，插件必须能报告已完成、未确认或状态未知。

阶段路线如下：
