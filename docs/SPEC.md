# Coterm 全局技术路线与架构规格

> **CLI**: `coterm`
> **产品定位**：面向软硬一体与边缘计算场景的人机协同通信终端。
> **文档职责**：定义长期有效的架构原则、模块边界、核心协议方向、安全基线与分阶段路线。具体模块的接口、状态机、测试方案和实现细节放在 `docs/technical-plan/` 下的阶段文档中。

## 1. 技术目标与不变量

Coterm 将本地终端、远程 Shell、串口和未来的工业通信协议统一成可观察、可审批、可恢复的会话。AI Agent 通过标准 MCP 使用这些能力，人类始终拥有可见、可暂停和可拒绝的控制权。

以下不变量约束所有后续设计：

1. **宿主拥有权威状态**：会话、输入仲裁、安全策略、命令块和审计状态由宿主管理，前端只负责呈现和交互。
2. **控制面与数据面分离**：连接管理、审批、状态变化使用结构化控制消息；终端字节流和高频日志按块传输并受背压和配额约束。
3. **能力先于工具**：插件先声明能力、权限和运行状态，宿主再把允许的能力映射成 MCP 工具。
4. **不确定性可见**：没有可靠退出码或命令边界时，系统必须表达 `unknown` 或置信度，不能伪造确定结果。
5. **人类控制覆盖所有副作用路径**：命令、按键、控制序列和协议写操作都必须经过同一套仲裁和策略管道。
6. **凭据不进入 Agent 上下文**：秘密只能经宿主的受控输入路径使用，不得出现在命令块、日志、MCP 返回值或遥测中。

## 2. 总体架构

```text
┌─────────────────────────────────────────────────────────────┐
│                         外部 AI Agent                       │
└──────────────────────────────┬──────────────────────────────┘
                               │ MCP Server
┌──────────────────────────────▼──────────────────────────────┐
│                         Coterm 宿主                          │
│  MCP 网关 | 会话管理 | 输入仲裁 | 安全策略 | 命令块存储       │
│  插件管理 | 凭据边界 | 审计与恢复 | UI 事件与数据订阅         │
└───────────────┬──────────────────────────┬──────────────────┘
                │ 宿主内部插件 RPC          │ Tauri IPC / 事件流
┌───────────────▼──────────────┐   ┌───────▼─────────────────┐
│       独立进程插件            │   │       前端工作台          │
│  能力声明 | 连接适配 | 数据流  │   │  xterm.js | 命令块视图    │
└───────────────┬──────────────┘   │  审批交互 | 会话管理      │
                │                  └─────────────────────────┘
       ┌────────▼────────┐
       │  物理/系统连接    │
       │ PTY | SSH | UART  │
       │ 未来的工业总线     │
       └──────────────────┘
```

宿主对外是 MCP Server。插件是宿主内部的通信适配器，默认不直接对外暴露 MCP；这样可以保证工具发现、权限检查、审批、取消和审计集中在一个边界内。若未来确实需要插件自定义领域工具，也必须先经过宿主的能力注册和安全策略映射。

## 3. 技术选型与职责边界

| 层 | 主要职责 | 约束 |
|---|---|---|
| Tauri + Rust 宿主 | 进程管理、连接会话、状态机、策略、凭据边界、MCP 网关、审计和恢复 | 是系统的权威状态源，不把关键安全逻辑放在前端 |
| 前端工作台 | xterm.js 渲染、标签/分屏、命令块视图、Ghost Text 交互、状态反馈 | 不直接管理物理连接，不自行决定审批结果 |
| 插件进程 | 具体协议连接、协议参数、领域数据解析和能力实现 | 只能使用 manifest 声明并获宿主授权的能力 |
| 物理连接适配器 | PTY、SSH、串口及未来工业总线的读写与取消 | 输出以原始数据块上报，不能假设所有协议都有退出码 |
| MCP 网关 | 对外提供稳定、受策略约束的工具和资源 | 所有有副作用的调用必须进入宿主仲裁管道 |

宿主采用 Tauri + Rust，前端采用 xterm.js。该选型适合桌面端、跨平台 I/O 和终端渲染，但不意味着 xterm.js 自身提供命令块、审批编辑器或安全边界；这些能力由宿主状态模型和前端辅助视图共同实现。

## 4. 核心协议方向

### 4.1 会话与连接适配器

每个会话由宿主分配稳定的 `session_id`，并关联一个连接适配器。适配器至少需要支持：连接、断开、读取数据块、写入数据块、请求取消、报告能力和报告连接状态。

适配器上报的是原始字节块及时间信息，宿主负责把数据解析成终端事件、命令生命周期事件和可供 UI/MCP 使用的结构化状态。适配器不得假定 Shell、提示符或退出码一定存在。

### 4.2 插件进程与内部 RPC

插件采用独立进程模型，以降低插件崩溃对宿主的影响。JSON-RPC over stdio 可以作为第一版控制面协议，但必须定义：

- manifest 和协议版本、握手、能力声明；
- 启动、心跳、超时、取消、崩溃和重启语义；
- 请求关联 ID、幂等性和错误分类；
- 数据块大小、队列上限、背压和恢复策略；
- 插件权限、来源信任、签名和完整性校验。

JSON-RPC 不承担无限速的终端数据流。高频输出必须使用有界的分块通道或等价的数据面设计。

### 4.3 MCP 对外接口

MCP 只暴露宿主确认过的稳定能力。第一阶段建议围绕以下操作建立最小闭环：

- 查询会话和连接状态；
- 按 ID、选中项或最近失败项读取命令块；
- 提出一条待执行的命令或协议写操作；
- 批准、拒绝、取消待执行操作；
- 订阅状态变化，或在不支持通知时轮询状态。

MCP Server 不假定可以向任意 Agent 注入“初始消息”。需要主动投递时，使用 MCP Resource、Notification 或明确的客户端扩展，并保留 Tool/Resource 拉取作为通用回退路径。

工具命名、参数版本、返回值上限、分页、超时和权限错误属于宿主的公共契约，不能由插件随意改变。

## 5. 终端语义与命令块

OSC 133 是现代 Shell 的优先完成信号，但它依赖 Shell 集成，不能作为所有 SSH、容器、tmux 或本地 Shell 的硬性前提。系统按证据等级选择命令边界：

1. 有可靠 Shell 标记时，记录开始、输出、结束和退出码；
2. 没有标记但有提示符规则时，记录启发式边界和置信度；
3. 串口或交互式场景无法确认时，记录原始流和 `unknown` 状态。

命令块至少包含会话标识、块标识、生命周期状态、发起时间、完成时间、命令或写入摘要、执行者、输出引用、截断信息、脱敏信息和完成证据。`exit_code` 必须允许为空；UI 的选择状态不属于持久化领域对象。

命令块输出需要保留原始数据和可展示文本之间的关系，支持 ANSI、编码、二进制或无法解析的内容。头尾截取只是展示策略，不能被描述为完整输出。

## 6. 人机协同与输入仲裁

宿主维护明确的操作状态，例如：`proposed`、`awaiting_approval`、`approved`、`queued`、`sending`、`running`、`interrupted`、`completed`、`unknown`、`rejected`。

人类输入到达时，宿主停止发送尚未提交的 Agent 输入，并记录已经写入底层连接的数据。已经进入 PTY、SSH 或串口缓冲区的字节不能撤回；是否发送 Ctrl-C、关闭连接或执行协议级取消，由适配器能力和用户策略决定。

Ghost Text 是审批交互的一种前端表现，不是安全边界。命令提议、任意按键、控制序列和协议写入都必须走同一套审批与审计路径。

## 7. 安全基线

### 7.1 凭据

凭据使用系统安全存储和宿主专用输入通道。no-echo 或密码提示符只能作为辅助信号，不能作为唯一隔离依据。原始凭据不得进入 Agent 上下文、命令块、日志、录屏、崩溃报告或插件普通返回值。

### 7.2 操作策略

高危保护默认启用并失败关闭。黑名单只能作为辅助规则，不能作为完整安全模型；策略应结合目标会话、工具能力、目标资源、工作目录和副作用等级。Bypass 只能减少普通审批，不能绕过强制人工确认的高风险操作。

### 7.3 插件信任

独立进程提供崩溃隔离，不等于操作系统沙箱。插件市场、在线安装和任意可执行文件加载必须建立在签名、权限、来源信任、版本兼容、更新回滚和审计机制之上，因此不作为第一阶段交付前提。

## 8. 性能、恢复与可观测性

- 终端输出采用有界内存、分段持久化或环形缓冲，禁止无上限完整缓存；
- 前端渲染、数据接收和历史存储相互解耦，允许丢弃渲染帧但不能阻塞控制面；
- 所有跨进程请求具备超时、取消、重试边界和关联 ID；
- 插件崩溃、连接断开和宿主重启后，系统能区分“已完成”“未确认”和“状态未知”；
- 关键操作保留结构化审计事件，避免只依赖终端截图或文本日志。

## 9. 分阶段路线

### 第一阶段：基础闭环

验证一个稳定连接协议、宿主权威状态、命令块生命周期、MCP 读取、审批执行、取消和凭据边界。详细方案目录为 `docs/technical-plan/phase-01-foundation/`，具体内容待评审后补充。

### 第二阶段：多协议与插件运行时

加入 SSH、串口和本地 PTY 的适配器差异处理，完善插件 manifest、内部 RPC、能力权限、背压、崩溃恢复和跨平台打包。

### 第三阶段：生态与高级工作台

在插件信任和更新机制稳定后，再考虑插件市场、离线开发包、SFTP、审计回放、主题编辑器和跨会话资产管理。

### 第四阶段：工业协议与多 Agent 策略

引入 CAN/Modbus 等领域插件，以及多 Agent 协同权限、资源锁和更细粒度的操作策略。
