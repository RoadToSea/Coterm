## 串口全双工与完整性

环境：Windows 11、CH340／COM6、riscv64 Linux 开发板、Python 3.9.4，8N1，无软硬件流控。本机 wch.cn 驱动版本 3.9.2024.9，驱动日期 2024-09-16；未升级或替换系统驱动。端口和设备节点仅为这次实测对象，不是项目默认连接要求。

最终代码使用独立 Windows overlapped 读写、有界通知合并和尾部提交。设备程序仅在内存运行，显式关闭 IXON／IXOFF／IXANY，两个方向使用独立负载并逐字节／校验和验证。

| 波特率 | 负载／持续情况 | 实际结论 |
|---|---|---|
| 115200 | 每轮每方向 64 KiB，共 31 轮，183.75 秒；每方向 2,031,616 字节 | 完整，事件缺口 0；每方向传输阶段约 11.39 KB/s |
| 500000 | 计划 600 秒；301.34 秒第 97 轮失败，此前 96 轮每方向 12,582,912 字节完整 | 当前批次少 90 字节，首差异偏移 100,544；未通过长期无损 |
| 1500000 | 计划 600 秒，第 26 轮失败 | 当前批次 131,044／131,072 字节，连续少 28，首差异偏移 72,736 |

两次高速失败后端回放与实时通知一致，事件缺口为 0，板端 UART frame／overrun／parity／brk／bufferOverrun 计数均为 0。500000 测试与本机 TCP 负载和工作区验证并行，不能据此声称已经排除调度影响。

独立 Python 标准库 ctypes／Win32 程序绕过 Coterm，也在 1500000 的第 24 轮少 668 字节，原生通信错误标志为 0。这把范围扩大到板端、USB 适配器、连线、Windows 驱动和调度，尚未证明其中任何一项为根因，也不能宣称 Coterm 软件已完全无责。

Python 3.9 的 raw 模式曾留下 IXOFF，捕获过混入的 XOFF；测试已经显式清除流控，但清除后仍存在上述缺失。请求更大系统队列仍失败，未保留这项修改；暂停读取不作为全双工修复。

**下一步**：相同负载更换适配器或系统交叉对照，继续区分原始缺字节、通知遗漏和历史淘汰。不能用短测、零 UART 错误或中间原型的通过替代最终长测。

范围不含完整 Runtime、WebView、xterm、MCP 和审批。上次退出已恢复 115200、ECHO／ICANON，确认 Shell 可用并释放端口；这不保证以后端口仍空闲。入口：[串口会话](../crates/coterm-driver/src/serial/session.rs)、[Windows IO](../crates/coterm-driver/src/serial/windows_io.rs)、[测速](../scripts/benchmark-serial.mjs)。

## TCP 吞吐与消费者缺口

环境：Windows 11（10.0.26200）、Ryzen 7 5800H、32 GiB、Rust 1.97.0、Node 22.22.2，release 本机回环。主测使用生产 DriverTask 队列、两个独立投放任务，双向 16 KiB 带序号记录，逐字节验证。每档 60 秒，MB/s 为十进制。

| 每方向投放目标 | RX MB/s | TX MB/s | 内容／广播缺口 |
|---|---:|---:|---|
| 5 MiB/s | 5.24 | 5.24 | 双向完整，0 |
| 10 MiB/s | 10.48 | 10.48 | 双向完整，0 |
| 50 MiB/s | 52.43 | 42.93 | 实际收到内容完整，0；TX 未达投放目标 |
| 100 MiB/s | 104.85 | 39.07 | 实际收到内容完整，0；TX 未达投放目标 |
| 不主动限速 | 134.15 | 37.29 | RX 少 1,132,928 字节，跳过 27 个事件，失败 |

50／100 MiB/s 两档不代表双向同速容量；测试也不包含完整 Runtime 账本、桌面渲染、MCP 或审批。

慢消费者负例为 5 MiB/s、3 秒、暂停 1500 ms：后端计数完整，消费少 6,539,000 字节，跳过 295 个事件，程序按非零退出。所有档位都发生正常有界历史淘汰，replayGap／readLinesDropped 为 true；实时消费完整与无限保留历史是两件事。

已修复 socket 小块输出导致的通知压力，以及前端把多块事件误判为缺口后逐页追赶的问题。无节流或消费者落后仍会失败，不能把 TCP 的可靠传输等同于应用通知无损保证。

**下一步**：若需要提高上限，先分开测生产／消费／显示路径并复现失败负载；不要只看 RX 计数或无限扩大队列。入口：[生产队列压测](../crates/coterm-driver/examples/tcp-task-throughput.rs)、[网络浏览器回归](../tests/network-drivers-browser.test.mjs)、[Node 校验器](../tests/throughput-frames.test.mjs)。
